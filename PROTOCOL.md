# Спецификация прикладного протокола

Данный документ описывает бинарный формат кадра, сериализацию, типы сообщений и алгоритмы работы P2P-узла.

### 1. Бинарный формат кадра
Обмен данными поверх TCP осуществляется с использованием строго определенного двоичного формата. Заголовок кадра имеет фиксированный размер 24 байта, все многобайтные числа кодируются в сетевом порядке (big-endian).

| Смещение | Поле | Размер | Тип | Описание |
| :--- | :--- | :--- | :--- | :--- |
| 0 | `version` | 1 байт | uint8 | Версия протокола (`PROTOCOL_VERSION = 1`) |
| 1 | `type` | 1 байт | uint8 | Тип сообщения |
| 2 | `flags` | 2 байта | uint16 | Флаги кадра (по умолчанию `0`) |
| 4 | `request_id` | 16 байт | bytes | Уникальный UUID (128 бит) для корреляции запросов и ответов |
| 20 | `payload_length`| 4 байта | uint32 | Длина полезной нагрузки (макс. 65536 байт) |
| 24 | `payload` | переменно | bytes | Сериализованные данные сообщения |

### 2. Формат сериализации и обоснование выбора

Для кодирования полезной нагрузки (`payload`) выбран стандарт **MessagePack**. В соответствии с Разделом 8 ТЗ, выбор формата обоснован сравнением четырёх альтернатив:

| Критерий | MessagePack | JSON | Protocol Buffers | CBOR |
| :--- | :--- | :--- | :--- | :--- |
| **Тип представления** | Бинарный | Текстовый (UTF-8) | Бинарный | Бинарный |
| **Оверхед кодирования** | Минимальный (1–2 байта на поле) | Высокий (кавычки, скобки, пробелы) | Минимальный (varint, tag-based) | Минимальный (RFC 8949) |
| **Поддержка сырых байт (bytes)** | Нативная (`bin format family`) | Требуется Base64 (+33% оверхед) | Нативная (`bytes`) | Нативная (`bstr`) |
| **Требование предкомпиляции схем** | Не требуется (schema-free) | Не требуется | Обязательно (`.proto` компилятор) | Не требуется |
| **Скорость парсинга в Python** | Высокая (C-extension `msgpack-python`) | Средняя | Высокая (C++ бэкенд) | Средняя (`cbor2`) |
| **Детерминизм и безопасность** | Высокая (нет eval/pickle RCE) | Высокая | Высокая | Высокая |

#### Обоснование выбора:
1. **Эффективность сетевого обмена:** P2P-протокол оперирует сырыми 32-байтными NodeID, открытыми ключами Ed25519 и хэшами SHA-256. В JSON эти данные требовали бы кодирования в Base64/Hex, увеличивая размер каждого кадра на 33–100%. MessagePack пакует бинарные поля без лишних накладных расходов.
2. **Гибкость в прототипировании без предкомпиляции:** В отличие от Protocol Buffers, MessagePack не требует генерации статических классов через `protoc`, что упрощает отладку распределённых структур данных и интеграцию в Python/Docker-окружение.
3. **Безопасность десериализации:** В отличие от встроенного в Python модуля `pickle`, MessagePack гарантирует строгую изоляцию типов и исключает возможность удалённого исполнения кода (RCE) при приёме вредоносного кадра.

### 3. Типы сообщений и схемы Payload
Текущая версия протокола поддерживает следующие коды сообщений.

* **`0x01` (PING)**: Запрос доступности контакта.
  {
    "sender": Contact,
    "timestamp_ms": uint64
  }
* **`0x02` (PONG)**: Ответ на запрос доступности.
  {
    "responder": Contact,
    "ping_timestamp_ms": uint64,
    "responder_timestamp_ms": uint64
  }
* **`0x03` (FIND_NODE_REQUEST)**: Поиск контактов, ближайших к целевому узлу.
  {
    "sender": Contact,
    "target_node_id": bytes[32]
  }
* **`0x04` (FIND_NODE_RESPONSE)**: Список найденных контактов. Возвращается до K_BUCKET_SIZE узлов, отсортированных по неубыванию XOR-расстояния.
  {
    "responder": Contact,
    "target_node_id": bytes[32],
    "contacts": Contact[]
  }
* **`0x7F` (ERROR)**: Ошибка протокола или обработки.
  {
    "code": string,
    "message": string
  }
Структура Contact в payload:
  {
    "node_id": bytes[32],
    "identity_algorithm": string ("Ed25519"),
    "identity_public_key": bytes,
    "host": string,
    "port": uint16
  }
4. Алгоритм формирования NodeID
NodeID вычисляется как хэш SHA-256 от сырых байтов публичного ключа Ed25519:
NodeID = SHA-256(canonical_encode(identity_public_key)). Сравнение расстояний между узлами выполняется на основе беззнаковой XOR-метрики.

5. Итеративный алгоритм FIND_NODE (Lookup)
Поиск маршрута в DHT работает следующим образом:

1)Из таблицы извлекаются до K_BUCKET_SIZE ближайших к цели контактов.

2)Формируется пул кандидатов, сортируемый по XOR-расстоянию до target_node_id.

3)Параллельно отправляются запросы FIND_NODE_REQUEST пулу из ALPHA = 3 неопрошенных контактов.

4)Новые валидные контакты из ответов добавляются в общий пул кандидатов.

5)Поиск останавливается, когда ни один из новых запросов не улучшает список ближайших известных узлов.
